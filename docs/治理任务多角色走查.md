# 治理相机任务多角色走查 · 2026-11-20

| 视角 | 发现的问题 | 修改结果 |
| --- | --- | --- |
| 管理员、组长 | 整改开始后，“问题 / 整改”数量漏算整改中的任务 | 项目、阶段和人员统计均纳入整改中 |
| 组长 | 已分派的受阻任务仍出现在待分派池，与待分派数量不同 | 池内只列团队待分派任务，协调受阻任务从“问题跟进”进入 |

| 两位执行人 | 问题和整改页混入其他人的任务，问题区重复出现 | 按当前执行人限定任务，问题区集中在“问题记录”，覆盖整改中的任务 |
| 切换身份 | 筛选条件、打开的详情和业务任务上下文可能从前一人带入 | 切换身份时重置项目范围、页签、筛选和选中的任务 |
| 执行人、抽查人 | 详情在未提交时显示待抽查，再次提交后可能沿用上一版结论 | 未提交显示“尚未提交”，有新提交版本显示“待抽查”，已抽查显示该版结论 |

## 浏览器走查

平台管理员创建基础信息治理批次并交给团队，组长分派给李同学。李同学按阶段筛选、打开任务并报告问题。陈同学的问题页无这项任务。组长在问题跟进中恢复任务，李同学打开业务页保存相机信息。

抽查人将首次提交退回。陈同学无法在自己的整改列表打开该任务，李同学可以进入并再次保存。抽查人对新版本给出通过结论，可在抽查记录中查看。

本轮使用独立浏览器中的演示数据。POI 挂载、事件配置在上轮验证了操作页切换，本轮跨角色提交和整改走的是基础信息治理路径。

## 两类治理角色与抽查范围 · 本轮验收

- 角色收敛为治理管理员和治理执行人。管理员承担批次、工作包分派、抽查和问题协调，两名执行人账号分别验证任务可见范围。
- 退回默认单路。“整个任务”采用现有工作包边界，只影响本阶段已提交且处于完成状态的相机。以实际可退回台数提示范围，分别退回原执行人。严重程度选填，整改要求必填。
- 批次采用有高度上限的紧凑列表，总览取最近三条。执行人任务以相机为行，将步骤、完成数和下一项操作并排，窄屏自动换行。
- Chrome 已验证两人任务隔离、三步执行、无价值跳过、第二步单独整改、工作包退回隔离和四种宽度。发布候选和发布前版本各自运行相同的 94 项回归检查，均为 87 项通过、7 项既有失败。
